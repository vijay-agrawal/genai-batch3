Technology Options for Field Identification:

🏷️ Named Entity Recognition (NER) RECOMMENDED

Uses ML models trained to identify and classify entities in regulatory text (field names, data types, thresholds, calculations, references).

Tools: spaCy (custom NER), Hugging Face Transformers (BERT/RoBERTa fine-tuned), AWS Comprehend, Google Cloud NLP

Traditional NER vs Contextual NER:
Traditional (CRF/rule-based): Pattern-matching, requires exact formats, poor generalization
Contextual (BERT/RoBERTa): Understands semantic context, infers entity types from surrounding text, handles novel formats
Pros:
  • High precision for structured extraction
  • Fast inference (ms for traditional, ~100ms for BERT)
  • Works offline, no API costs
  • Consistent, deterministic results
  • Custom entity types for finance domain
  • Contextual models: Infer entities from context (e.g., "the regulator" → MAS)
  • Contextual models: Better zero-shot generalization to new formats
Cons:
  • Requires labeled training data (~500+ examples)
  • Traditional only: Struggles with novel field formats
  • Traditional only: Cannot infer implicit relationships
  • Contextual models need GPU for efficient inference
  • Fine-tuning still needed for domain-specific entities

🤖 Large Language Models (LLM) FLEXIBLE

Uses foundation models with prompting/few-shot learning to extract fields, understand context, and infer data mappings from natural language requirements.

Tools: GPT-4/GPT-4o, Claude 3, Gemini Pro, Llama 3 (self-hosted)

Pros:
  • Zero-shot capability - no training needed
  • Understands complex context and nuance
  • Can infer implicit requirements
  • Handles varied document formats
  • Explains reasoning for mappings
Cons:
  • Higher latency (1-10 seconds)
  • API costs ($0.01-0.10 per document)
  • Non-deterministic outputs
  • May hallucinate field names
  • Requires output validation

📐 Rule-Based / Regex Pattern Matching TRADITIONAL

Uses handcrafted regular expressions and parsing rules to extract fields based on known document structure and formatting conventions.

Tools: Python re module, pyparsing, ANTLR, custom parsers

Pros:
  • 100% deterministic and explainable
  • Extremely fast execution
  • No external dependencies
  • Easy to audit and validate
  • Zero operational costs
Cons:
  • Brittle to format changes
  • High maintenance burden
  • Cannot handle ambiguity
  • Requires deep domain expertise
  • Poor generalization to new docs

Technology Options for Text-to-SQL:

🧠 LLM with RAG (Retrieval-Augmented Generation) RECOMMENDED

Combines LLMs with schema retrieval - embeds schema metadata, retrieves relevant tables/columns, and generates contextually-aware SQL with examples.

Tools: LangChain SQL Agent, LlamaIndex, Vanna.ai, GPT-4 + pgvector/Pinecone for schema embeddings

Pros:
  • Handles large schemas (1000+ tables)
  • Learns from query history
  • Adapts to schema changes automatically
  • Provides natural language explanations
  • High accuracy with few-shot examples
Cons:
  • Requires vector DB infrastructure
  • Higher latency (2-5 seconds)
  • Complex prompt engineering needed
  • May generate syntactically incorrect SQL
  • Needs SQL validation layer

🎯 Specialized Text-to-SQL Models HIGH ACCURACY

Purpose-built models fine-tuned specifically for SQL generation tasks, trained on Spider/WikiSQL benchmarks with schema encoding.

Tools: SQLCoder (Defog), DIN-SQL, RESDSQL, NumbersStation/NSText2SQL, Codex fine-tuned

How Schema is Provided to Models:

1. Schema Serialization (in prompt):
CREATE TABLE gl_accounts (account_id INT PK, account_name VARCHAR, balance DECIMAL);
CREATE TABLE transactions (txn_id INT PK, account_id INT FK, amount DECIMAL);

2. Schema Linking (two-stage):
Stage 1: Identify relevant tables/columns from question → ["gl_accounts", "balance"]
Stage 2: Include only filtered schema in prompt (reduces 1000 tables → 5-10)

3. Schema Encoding Methods:
DDL formatCREATE TABLE statements - most common, models trained on this
Pipe formattable_name(col1, col2, col3*) - compact, * marks PK
JSON schema{"table": "accounts", "columns": [...]} - structured
Graph encodingEncode FK relationships as edges - for GNN-based models
Handling Large Schemas (1000+ tables):
  • Embedding-based retrieval: Embed table/column descriptions, retrieve top-k relevant
  • Question-to-schema matching: Use NER to extract entities, match to table names
  • Hierarchical selection: First select schema (database), then tables, then columns
  • Schema summarization: Generate natural language descriptions of tables
Pros:
  • State-of-the-art SQL accuracy (85%+)
  • Optimized for SQL syntax
  • Can run locally (7B-15B params)
  • Lower cost than general LLMs
  • Better complex JOIN handling
Cons:
  • Less flexible for edge cases
  • Requires GPU for inference
  • Limited to SQL generation only
  • May need fine-tuning for Oracle dialect
  • Smaller context windows (4K-8K typical)

📝 Template-Based with Slot Filling DETERMINISTIC

Tools: Jinja2 SQL templates, Custom DSL, Apache Calcite, dbt macros

🔧 Fine-Tuned Domain-Specific Models HIGHEST ACCURACY

Base LLMs or Text-to-SQL models fine-tuned on organization-specific query patterns, schema conventions, and historical SQL queries for maximum accuracy.

Tools: OpenAI Fine-tuning API, LoRA/QLoRA adapters, Hugging Face PEFT, Modal/Anyscale for training, Weights & Biases for tracking

Fine-tuning Approaches:
Full fine-tuning: Update all weights - best accuracy, expensive ($1000s GPU hours)
LoRA/QLoRA: Train adapter layers only - 90% of accuracy at 10% cost
Prompt tuning: Learn soft prompts - fastest, least accurate
Pros:
  • Learns org-specific naming conventions
  • Captures tribal knowledge in queries
  • 90%+ accuracy on known patterns
  • Handles Oracle/DB2 dialect nuances
  • Can encode business rules in model
Cons:
  • Requires 1000+ query examples
  • Expensive GPU training ($500-5000)
  • Risk of overfitting to training data
  • Needs retraining for schema changes
  • Model versioning complexity

🏗️ Agentic Design Patterns Applied

Definition: Proven architectural patterns for building reliable, scalable AI agent systems.

1. ReAct (Reason + Act)

Interleaves reasoning traces with actions for transparent decision-making.

Thought: Need capital adequacy data
Action: query_gl_database
Observation: Got balance data
Thought: Now calculate CAR ratio
Action: calculate_ratio
Result: CAR = 14.2%

2. Chain of Thought (CoT)

Breaks complex reasoning into explicit intermediate steps.

Step 1: Identify Tier 1 capital components
Step 2: Sum CET1 + AT1 capital
Step 3: Calculate risk-weighted assets
Step 4: Tier1 Capital / RWA = CAR
Step 5: Compare against 10.5% threshold

3. Self-Ask

Agent asks and answers sub-questions to decompose complex queries.

Q: What is 's capital adequacy?
Sub-Q1: What is Tier 1 capital? → $45B
Sub-Q2: What are RWAs? → $320B
Sub-Q3: What is the formula? → T1/RWA
Answer: 45/320 = 14.06%

4. Plan and Execute

Separates planning from execution for complex multi-step tasks.

PLAN:
1. Parse MAS 610 requirements
2. Map fields to GL accounts
3. Generate SQL queries
4. Extract data
5. Validate results
EXECUTE: [Run each step sequentially]

5. Supervisor Pattern

Orchestrator agent delegates to specialized worker agents.

Supervisor: "Need capital report"
 → Delegate to: RequirementsAgent
 → Delegate to: SQLAgent
 → Delegate to: ValidationAgent
 → Aggregate results
 → Return final report

6. Hierarchical Agents

Multi-level agent hierarchy for complex organizational structures.

L1: Compliance Director (strategy)
 └─ L2: Report Manager (coordination)
     ├─ L3: Data Team (extraction)
     ├─ L3: Validation Team (QA)
     └─ L3: Filing Team (submission)

Tool Definition Pattern

@tool
def execute_sql_query(query: str, database: str = "oracle_gl") -> Dict[str, Any]:
    """Execute a SQL query against the specified database.

    Args:
        query: The SQL query to execute (SELECT only)
        database: Target database connection name

    Returns:
        Dict with 'data' (results), 'columns' (names), 'row_count', 'execution_time'
    """
    # Validate query is read-only
    if not query.strip().upper().startswith("SELECT"):
        raise ValueError("Only SELECT queries allowed")

    # Execute with connection pooling
    with get_connection(database) as conn:
        result = conn.execute(text(query))
        return {
            "data": result.fetchall(),
            "columns": result.keys(),
            "row_count": result.rowcount,
            "execution_time": result.execution_time
        }

# Bind tools to agent
sql_agent = Agent(
    role="SQL Expert",
    tools=[execute_sql_query, get_table_schema, validate_sql_syntax]
)

LangGraph A2A via State

# A2A via shared state in LangGraph
class A2AState(TypedDict):
    messages: Annotated[List[Message], add_messages]
    sender: str
    recipient: str
    task_result: Any

def sql_agent_node(state: A2AState) -> A2AState:
    # Read message from previous agent
    last_msg = state["messages"][-1]

    # Process and respond
    sql = generate_sql(last_msg.content)

    # Send to next agent via state
    return {
        "messages": [AIMessage(content=sql)],
        "sender": "sql_agent",
        "recipient": "extractor_agent",
        "task_result": {"query": sql}
    }

# Router decides next agent based on state
def route_message(state: A2AState) -> str:
    return state["recipient"]
